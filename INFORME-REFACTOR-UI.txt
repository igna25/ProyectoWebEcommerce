────────────────────────────────────────────────────────────────────────────────
1.1  Motivación y criterios de diseño
────────────────────────────────────────────────────────────────────────────────

El objetivo fue modernizar la interfaz partiendo de una base funcional pero
visualmente inconsistente. Problemas detectados antes del refactor:

  • Elementos HTML inválidos: <Button> de Headless UI conteniendo <Link>,
    y <Link> conteniendo <Button>. Esto genera nodos interactivos anidados,
    viola la especificación HTML5 y produce comportamiento impredecible en
    lectores de pantalla y eventos de click.

  • Paleta de colores mezclada: botones con bg-blue-500, bg-blue-600,
    bg-blue-400 sin un color de marca definido.

  • Falta de jerarquía visual: cards sin sombra, formularios sin card
    contenedora, navbar sin height fija.

  • Inconsistencia en bordes: algunos elementos con rounded, otros con
    rounded-lg, otros sin borde.

  • Scroll horizontal en mobile por falta de padding lateral.

NOTA TÉCNICA — Nodos interactivos anidados:
  Los nodos interactivos anidados (<button> dentro de <a> o viceversa)
  son ilegales según la especificación HTML5. El navegador los intenta
  corregir automáticamente, pero el resultado es impredecible: el click
  puede dispararse dos veces o no propagarse correctamente. Además, los
  lectores de pantalla (NVDA, VoiceOver) reportan ambos roles, generando
  confusión en usuarios con discapacidad visual.

Criterios adoptados para el refactor:

  • Color de marca único: #004AAD (hover: #003d8f).
  • Elementos interactivos limpios: todos son <Link> o <button> directos,
    sin anidamiento.
  • Bordes redondeados consistentes: rounded-xl para inputs y botones
    primarios, rounded-2xl para cards y paneles.
  • Sombra coherente: shadow-sm en cards en reposo, shadow-md en hover.
  • Fondo de la aplicación: gray-50 o gray-100 (nunca blanco puro en el
    contenedor raíz).

NOTA: El color #004AAD no fue elegido arbitrariamente — ya existía como
themeColor en el manifest PWA (src/app/layout.tsx → viewport.themeColor).
El refactor simplemente alineó la UI con la identidad ya definida para
la app instalable.

BEST PRACTICE — Tokens en tailwind.config.ts:
  Usar clases arbitrarias como bg-[#004AAD] es funcional pero es un
  anti-patrón para proyectos grandes. La forma correcta es definirlos en
  tailwind.config.ts:

    theme: {
      extend: {
        colors: {
          brand: {
            DEFAULT: '#004AAD',
            dark:    '#003d8f',
          }
        }
      }
    }

  Con esto se puede escribir bg-brand y hover:bg-brand-dark, que son más
  legibles, fáciles de mantener y soportan el motor de purga de Tailwind.

1.3  NavBar — barra de navegación principal
────────────────────────────────────────────────────────────────────────────────

Archivo: src/app/ui/shared/NavBar.tsx

Problema original:
  • La raíz era un <div>, no semánticamente correcto para una barra de
    navegación.
  • <HomeButton> internamente tenía <Button><Link>, nodo interactivo anidado.

  • Se fijó height con h-14 (56px). Se usó sticky top-0 z-50 para que
    el navbar acompañe el scroll.
  • Los botones de carrito y historial ahora muestran solo el icono en
    mobile y el texto completo en sm+: <span className="hidden sm:inline">.

NOTA TÉCNICA — next/image con fill:
  La prop fill de Next.js Image requiere que el contenedor padre tenga
  position: relative y dimensiones definidas. Sin esto, la imagen no
  se renderiza o desborda. El patrón correcto es:

    <div className="relative aspect-[4/3] overflow-hidden rounded-t-2xl">
      <Image src={...} alt={...} fill className="object-cover" />
    </div>

  El uso de aspect-[4/3] (Tailwind v3+) garantiza que el contenedor
  siempre mantenga la proporción 4:3 independientemente del ancho.

NOTA TÉCNICA — focus-within vs focus:
  focus aplica estilos cuando el elemento MISMO tiene el foco.
  focus-within aplica estilos cuando el elemento O CUALQUIER DESCENDIENTE
  tiene el foco. Útil para inputs decorados con iconos donde el icono es
  un hermano del input, no el input mismo.

  Ejemplo:
    <div className="focus-within:ring-2 focus-within:ring-[#004AAD]">
      <MagnifyingGlassIcon /> {/* no tiene foco */}
      <input />               {/* cuando este tiene foco, el div reacciona */}
    </div>

────────────────────────────────────────────────────────────────────────────────
2.1  Overflow horizontal — diagnóstico y solución
────────────────────────────────────────────────────────────────────────────────

Síntoma: scroll horizontal en mobile en las páginas dashboard y landing.

Diagnóstico:
  Las páginas tenían divs con max-w-7xl mx-auto SIN px-4:

    // Sin padding: puede causar overflow en mobile
    <div className="mx-auto max-w-7xl">
    <div className="mx-auto max-w-7xl py-4">

  max-w-7xl (1280px) en mobile actúa como width: 100% del viewport.
  Sin px-4, el contenido hijo se renderizaba desde el pixel 0, llegando
  exactamente al borde del viewport. Elementos con min-width implícito
  (inputs, imágenes) podían exceder el viewport por pocos píxeles.

Solución A — Corrección estructural:

    // Con padding horizontal seguro
    <div className="mx-auto max-w-7xl px-4">
    <div className="mx-auto max-w-7xl px-4 py-4">

  px-4 = 16px cada lado → 32px totales de margen horizontal seguro.

Solución B — Barrera de seguridad en globals.css:

    /* globals.css */
    html, body {
      overflow-x: hidden;
    }

ADVERTENCIA: overflow-x: hidden en el body puede interferir con
position: sticky en algunos navegadores (específicamente Safari).
En este proyecto no hay sticky en el body directo, sino en el nav
y en el panel del carrito, que están dentro del flujo normal y
no se ven afectados.

────────────────────────────────────────────────────────────────────────────────
2.6  Tipografía fluida
────────────────────────────────────────────────────────────────────────────────

  Componente / Elemento      Mobile       Desktop (sm+)
  ─────────────────────────────────────────────────────
  dashboard/page.tsx — h1    text-2xl     sm:text-4xl
  HomePage.tsx — h2          text-xl      sm:text-3xl
  ProductDetails — h1        text-xl      sm:text-2xl
  ProductDetails — precio    text-2xl     sm:text-3xl

Patrón general: text-{tamaño-mobile} sm:text-{tamaño-desktop}
El tamaño mobile es siempre un escalón por debajo del desktop.

AVANZADO — Tipografía fluida con clamp():
  Tailwind no tiene tipografía fluida nativa. Para escalado continuo
  entre breakpoints se puede usar CSS puro:

    /* Escala de 20px (mobile) a 36px (desktop) entre 320px y 1280px */
    font-size: clamp(1.25rem, 1.25rem + 1.5vw, 2.25rem);

  Para usar en Tailwind: extender el tema con un plugin o usar clase
  arbitrary [font-size:clamp(1.25rem,1.25rem+1.5vw,2.25rem)]. El patrón
  de breakpoints es suficiente para la mayoría de proyectos.

────────────────────────────────────────────────────────────────────────────────
3.1  Motivación y enfoque del refactor admin
────────────────────────────────────────────────────────────────────────────────

La interfaz de admin original tenía una identidad visual diferente a la
parte pública: bordes rectos, sin sombras, colores desconectados del
sistema de la marca, y sin diseño responsive real en mobile.

Objetivos del refactor admin:
  • Alinear visualmente admin con la UI pública: mismos tokens de color,
    mismo sistema de cards (rounded-2xl shadow-sm border-gray-100),
    mismos patrones de inputs y botones.
  • No cambiar la lógica ni la estructura de datos. Solo estilos y
    pequeños ajustes de layout.
  • Hacer la interfaz mobile-friendly: el sidebar desktop se oculta en
    mobile y se reemplaza por un header fijo + drawer lateral simple.
  • Reemplazar la animación de apertura del menú mobile (clip-path
    circular con Framer Motion) por una transición CSS estándar (slide
    desde la izquierda), más familiar para el usuario y menos costosa
    en rendimiento.

────────────────────────────────────────────────────────────────────────────────
3.4  HeaderMobile — header fijo + drawer lateral
────────────────────────────────────────────────────────────────────────────────

Archivo: src/app/ui/admin/sideBar/HeaderMobile.tsx

Este fue el cambio más significativo del refactor admin.

ANTES (Framer Motion — clip-path circular):
  • El menú era un overlay de pantalla completa (fixed inset-0) con una
    animación de apertura en forma de círculo que se expandía desde la
    esquina superior derecha.
  • Técnica: clipPath: `circle(${height * 2 + 200}px at 100% 0)`.
  • Cada ítem de navegación tenía su propia animación de entrada
    (staggerChildren con opacity y translateY).
  • La dependencia era framer-motion (ya instalada en el proyecto).
  • PROBLEMA: el componente era fixed pero NO renderizaba una barra
    visible en estado cerrado. El botón hamburguesa flotaba sobre el
    contenido sin ningún fondo de respaldo, provocando que el logo del
    menú se superpusiera visualmente sobre las cards del dashboard.

DESPUÉS (CSS transition — slide desde la izquierda):
  • Se separan dos responsabilidades en dos elementos distintos:

    1. HEADER BAR (siempre visible en mobile):
       <header className="md:hidden fixed top-0 left-0 right-0 z-40 h-12
         bg-gray-900 flex items-center justify-between px-4 border-b border-gray-700">

       - z-40 (por debajo del drawer z-50 cuando está abierto).
       - h-12 = 48px de altura fija.
       - Logo a la izquierda, botón hamburguesa/X a la derecha.
       - El ícono cambia dinámicamente: Menu cuando cerrado, X cuando abierto.

    2. DRAWER (panel lateral deslizante):
       <nav className="md:hidden fixed top-0 left-0 z-50 h-full w-64
         bg-gray-900 transform transition-transform duration-300 ease-in-out
         translate-x-0 / -translate-x-full">

       - z-50 para estar por encima del header bar y el contenido.
       - w-64 = 256px de ancho.
       - transform + transition-transform: la transición CSS es más
         performante que la animación JS de Framer Motion.
       - translate-x-0 cuando open=true, -translate-x-full cuando closed.

    3. OVERLAY (fondo oscuro al abrir):
       {isOpen && (
         <div className="md:hidden fixed inset-0 z-40 bg-black/50"
           onClick={closeMenu} />
       )}

       - Se renderiza solo cuando el menú está abierto (conditional render).
       - Al hacer click en el overlay se cierra el menú.
       - bg-black/50 = negro con 50% de opacidad (Tailwind v3 sintaxis).

  • Estado del menú: useState simple en lugar de useCycle de Framer Motion.
  • Se eliminó framer-motion del componente.
    (framer-motion sigue en el proyecto, usada en otras partes)

LAYOUT FIX — padding top en el contenido:
  El admin layout fue actualizado para agregar padding-top en mobile
  que compense la barra header fija:

  Antes:  <div className="flex flex-col pt-2 px-4 ...">
  Después: <div className="flex flex-col pt-14 md:pt-2 px-4 ...">

  pt-14 = 56px > h-12 (48px) del header → margen de seguridad de 8px.
  md:pt-2 → en desktop (con sidebar) vuelve al padding original.

  Archivo: src/app/admin/layout.tsx

Estructura de la página:

────────────────────────────────────────────────────────────────────────────────
4.1  Semántica HTML y accesibilidad
────────────────────────────────────────────────────────────────────────────────

La semántica HTML correcta beneficia:
  a) SEO: los crawlers entienden mejor la estructura del contenido.
  b) Accesibilidad: lectores de pantalla anuncian los roles correctamente.
  c) Mantenibilidad: el código es más fácil de entender.

Etiquetas semánticas usadas:
  • <nav aria-label="...">    → Landmark de navegación.
  • <header>                   → Encabezado de sección.
  • <main>                     → Contenido principal (ya existía).
  • <h1>/<h2>/<h3>             → Jerarquía de encabezados respetada.
  • <section>                  → Agrupación temática de contenido.

Regla: los elementos interactivos (<a>, <button>) no deben anidarse
entre sí. La especificación HTML5 lo prohíbe explícitamente.

────────────────────────────────────────────────────────────────────────────────
4.2  Link-as-button vs button nativo
────────────────────────────────────────────────────────────────────────────────

Regla de decisión:

  Usar <Link>  cuando: la acción navega a una URL.
  Usar <button> cuando: la acción no navega (muta estado, llama API, abre modal).

  // CORRECTO: link que parece botón
  <Link href="/admin/ventas"
    className="px-4 py-2 bg-[#004AAD] text-white rounded-xl">
    Ver ventas
  </Link>

  // CORRECTO: botón de acción
  <button onClick={() => signOut()}
    className="px-4 py-2 ...">
    Cerrar sesión
  </button>

  // INCORRECTO: nodo interactivo anidado
  <Button> {/* renderiza como <button> */}
    <Link href="/ventas">Ver ventas</Link>
  </Button>

La técnica link-as-button consiste en aplicar estilos visuales de botón
(padding, background, border-radius, font-weight) a un elemento <Link>
o <a>. El elemento sigue siendo semánticamente un enlace.

────────────────────────────────────────────────────────────────────────────────
4.3  Tokens de diseño vs clases Tailwind directas
────────────────────────────────────────────────────────────────────────────────

Nivel 1 — Clases directas (actual, funcional pero no ideal):
  bg-[#004AAD] hover:bg-[#003d8f]

Nivel 2 — Tokens en tailwind.config.ts (recomendado):
  theme.extend.colors.brand.DEFAULT = '#004AAD'
  theme.extend.colors.brand.dark    = '#003d8f'
  → Se usa como: bg-brand hover:bg-brand-dark

Nivel 3 — CSS Variables (para theming dinámico):
  :root { --color-brand: #004AAD; }
  → Se usa como: bg-[var(--color-brand)]
  → Permite cambiar el tema en runtime (dark mode, temas de cliente).

El proyecto actual usa Nivel 1. Para una evolución, Nivel 2 es el
siguiente paso natural.

────────────────────────────────────────────────────────────────────────────────
4.5  Headless UI — Button y sus diferencias con <button>
────────────────────────────────────────────────────────────────────────────────

Headless UI es una librería de componentes accesibles sin estilos.
Su componente <Button> renderiza un <button> nativo, pero agrega:

  • Gestión automática de data-active, data-hover, data-focus attributes.
  • Soporte para disabled con manejo de ARIA correcto.
  • Compatibilidad con grupos (ButtonGroup).

En este proyecto, <Button> de Headless UI se usa cuando se necesitan
los data-attributes para estilos condicionales:

  className="... data-[hover]:bg-red-100 data-[active]:scale-95"

Si no se necesitan los data-attributes, un <button> nativo es igualmente
válido y no agrega peso de dependencia.

IMPORTANTE: <Button> de Headless UI NO debe contener elementos interactivos
(<Link>, <a>, otro <button>). Esto generaría el anti-patrón de nodos
interactivos anidados discutido en 4.1.

────────────────────────────────────────────────────────────────────────────────
4.6  Animaciones CSS vs Framer Motion
────────────────────────────────────────────────────────────────────────────────

Framer Motion:
  PROs: animaciones complejas (drag, layout animations, spring physics),
        orquestación (staggerChildren), animaciones de salida (exit).
  CONs: bundle size (~50KB gzipped), overhead de JS en cada frame,
        más complejo de mantener para animaciones simples.

CSS Transitions (transform + transition):
  PROs: ejecutan en el compositor del browser (GPU), no bloquean el JS
        thread, zero bundle size adicional, simples de entender.
  CONs: limitadas a propiedades animables con CSS, sin spring physics,
        sin animaciones de salida sin JS adicional.

Decisión tomada en el refactor admin:
  La animación de apertura del menú mobile (clip-path circular) fue
  reemplazada por una transición CSS (translate-x) porque:
  1. Es una animación simple: slide desde la izquierda.
  2. CSS transitions tienen mejor rendimiento en mobile (compositor thread).
  3. Elimina la dependencia de framer-motion de este componente.
  4. La animación es más predecible y familiar para el usuario.

────────────────────────────────────────────────────────────────────────────────
4.7  Patron "Client Component Shell" en Next.js App Router
────────────────────────────────────────────────────────────────────────────────

Next.js App Router tiene Server Components por defecto. Para manejar
interactividad con hooks (useState, useEffect) se necesitan Client Components
marcados con "use client".

El problema original en las páginas admin era que todo el componente de
página era un Server Component, lo que impedía:
  • Manejo de estado offline (navigator.onLine).
  • Fetch de datos desde el cliente con manejo de errores.
  • Mostrar spinners de carga.

Solución: patrón "Client Component Shell":

  // src/app/admin/activos/page.tsx (Server Component — ligero)
  import { Suspense } from "react";
  import AdminProductsPage from "@/app/ui/admin/AdminProductsPage";

  export default function Page() {
    return (
      <Suspense fallback={<div>Cargando...</div>}>
        <AdminProductsPage active={true} />
      </Suspense>
    );
  }

  // src/app/ui/admin/AdminProductsPage.tsx (Client Component — lógica)
  "use client";
  export default function AdminProductsPage({ active }) {
    const [products, setProducts] = useState([]);
    useEffect(() => { /* fetch con manejo offline */ }, []);
    return <ProductsListAdmin products={products} />;
  }

Ventajas:
  • El Server Component (page.tsx) puede exportar metadata, hacer auth
    server-side, y es más rápido de renderizar.
  • El Client Component (AdminProductsPage) maneja toda la interactividad.
  • Suspense en el Server Component provee el fallback de carga.

────────────────────────────────────────────────────────────────────────────────
4.8  clsx — composición condicional de clases
────────────────────────────────────────────────────────────────────────────────

clsx es una utilidad para componer strings de clases CSS condicionalmente.
Se usa en el proyecto en UpdateComponent.tsx y otros formularios.

  import clsx from "clsx";

  // Ejemplo básico
  clsx("base-class", isActive && "active-class", isError && "error-class")
  // → "base-class active-class" si isActive=true, isError=false

  // Con objetos (sintaxis alternativa)
  clsx({ "bg-red-100": isError, "bg-green-100": isSuccess })

  // En el proyecto (input de formulario):
  clsx(
    "block w-full rounded-xl border bg-gray-50 py-2 px-3 text-sm",
    "focus:outline-none focus:ring-2 focus:ring-[#004AAD]",
    errors.productName ? "border-red-400" : "border-gray-200",
  )

ALTERNATIVA: cn() con tailwind-merge.
  tailwind-merge resuelve conflictos entre clases Tailwind del mismo tipo
  (ej: "p-2 p-4" → "p-4"). Es más robusto que clsx solo cuando se
  combinan clases de diferentes orígenes (props + base).

  import { clsx } from "clsx";
  import { twMerge } from "tailwind-merge";
  export function cn(...inputs) { return twMerge(clsx(inputs)); }

A.2  Reglas de accesibilidad aplicadas
────────────────────────────────────────────────────────────────────────────────

  1. Todo botón que solo muestra un icono debe tener aria-label con
     descripción textual de la ACCIÓN (ej: aria-label="Cerrar menú").

  2. La barra de navegación debe usar la etiqueta semántica <nav> con
     aria-label descriptivo.

  3. Los elementos interactivos (<a>, <button>) no deben anidarse entre sí.

  4. Los colores de texto sobre fondo deben cumplir ratio de contraste
     mínimo de 4.5:1 (WCAG AA) para texto normal, 3:1 para texto grande.

  5. Los modales deben tener un backdrop oscuro para comunicar el estado
     de bloqueo del fondo.

  6. Los inputs de formulario deben tener labels asociados explícitamente
     con htmlFor={id} / id={id}.

  7. Los estados de error deben comunicarse con texto visible, no solo
     con color (no depender solo de "el borde se pone rojo").

────────────────────────────────────────────────────────────────────────────────
A.3  Glosario de clases Tailwind clave
────────────────────────────────────────────────────────────────────────────────

  overflow-hidden       Recorta el contenido que desborda el contenedor.
                        Necesario con border-radius para que las esquinas
                        funcionen en imágenes.

  transition-shadow     Anima solo la propiedad box-shadow. Más performante
                        que transition-all que anima TODAS las propiedades.

  truncate              overflow:hidden + text-overflow:ellipsis +
                        white-space:nowrap. Requiere width definido o min-w-0
                        en contexto flex.

  shrink-0              flex-shrink: 0. El elemento no se encoge aunque
                        el contenedor flex no tenga espacio.

  min-w-0               Permite que un flex child se encoja por debajo de su
                        tamaño de contenido mínimo. Habilita el uso de
                        truncate dentro de flex containers.

  inset-0               top:0 right:0 bottom:0 left:0 en una sola clase.
                        Cubre completamente el contenedor posicionado padre.

  aspect-[4/3]          Ratio de aspecto arbitrario 4:3 (Tailwind v3+).
                        Mantiene proporciones al escalar con CSS puro.

  ring-offset-1         Espacio blanco entre el elemento y el anillo de foco.
                        Mejora la visibilidad del focus ring.

  bg-black/50           Negro con 50% de opacidad. Sintaxis de opacidad de
                        color en Tailwind v3: color/opacidad.

  divide-y              Aplica border-top a todos los hijos excepto el
                        primero. Equivale a :not(:first-child) { border-top }.

  tracking-wide         letter-spacing: 0.05em. Útil para etiquetas en
                        mayúsculas (uppercase tracking-wide).

  -translate-y-1/2      translateY(-50%). Combinado con top-1/2 centra
                        verticalmente un elemento absoluto.

  pointer-events-none   El elemento no responde a eventos de mouse/touch/click.
                        El evento "atraviesa" hacia el elemento de abajo.

  pointer-events-auto   Restaura los eventos del puntero. Útil para
                        re-habilitar hijos específicos dentro de un padre
                        con pointer-events-none.

A.4  Anti-patrones detectados y su corrección
────────────────────────────────────────────────────────────────────────────────

  Anti-patrón                          Corrección aplicada
  ─────────────────────────────────────────────────────────────────────────────
  <Button><Link href="..."></Link></Button>  → <Link href="..." className="...px-4 py-2...">
  <Link href="..."><Button>...</Button></Link> → <Link href="..." className="...px-4 py-2...">
  div como contenedor de nav           → <nav aria-label="...">
  Paleta de colores inconsistente      → Token único #004AAD
  max-w-7xl sin px-4 en mobile         → Agregar px-4 al contenedor
  Header mobile sin espacio reservado  → pt-14 md:pt-2 en el contenido
  Animación compleja con Framer Motion → CSS transition (translate-x)
  para un simple slide de menú
  Icono de búsqueda sin texto aria     → El input tiene placeholder descriptivo
